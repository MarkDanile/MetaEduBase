## Root Causes

| 根因 | 类型 | 说明 |
|------|------|------|
| 需求 AC 与真实验证路径脱节 | 需求塑形不足 | `REQ-002-1`、`REQ-005`、`REQ-010` 说明复杂需求只写“完成能力”不够，必须把 UI 交互矩阵、真实 DB / e2e、RAG 真实数据路径写进验收。 |
| 多 Slice 任务天然容易产生事实源漂移 | 流程问题 | `REQ-010`、`TD-032`、`DOC-042` 的得分都被 PR 范围、work-log 标题、占位和完成态声明拖低。 |
| 验证声明容易把主观判断包装成通过 | 执行习惯 | 多次复盘都出现“相关路径通过”与“全量命令通过”混用；评分体系已经能识别，但执行者仍需在提交前回读命令、退出码、环境和范围。 |
| 脚本门禁有效，但不应无限扩大规则正文 | 规则治理 | `DOC-056`、`DOC-059` 这类小脚本 / 短入口收益高；反之，长规则容易被忽略。后续优先把可机械检查的问题脚本化。 |
| Follow-up 链条是价值信号，也是成熟度信号 | 交付模式 | 40% 返工率不等于失败；它说明评审能发现并入账问题。但长期目标应降低“原任务关闭后才发现实质 AC 缺口”的比例。 |

## Conclusion

这套 Harness 已经证明有价值：没有低于 70 分的失控交付，多数任务能被控制在 80 分以上，并且问题会被转成稳定 follow-up。当前主要短板不是规则缺失，而是需求类任务的一次性验收完整度、真实数据验证、以及多事实源完成态同步。下一阶段应保持规则瘦身，继续把高频、低成本、可机械判断的问题转成脚本门禁。
