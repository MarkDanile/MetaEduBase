# Review Scorecard — 任务评审评分卡

本文件用于 Codex、Claude Code、Trae、人工 Review 或 PR Review 后的统一评价。目标不是替代质量门禁，而是把每次评审沉淀成可比较的数据：任务是否完成、风险是否可接受、follow-up 是否入账、规则是否需要改进。

## 使用时机

- AI IDE 交叉复核任务完成情况。
- PR 合并前后需要判断是否可关闭任务。
- 阶段性复盘需要汇总多个任务的交付质量。
- 同类问题重复出现，需要判断是否补规则或脚本门禁。

轻量任务可以只给总分和关键扣分项；复杂需求、技术债、跨 AI 交接任务应使用完整评分表。

## 评分维度

总分 100 分。评分必须引用代码、文档、PR、测试命令或验收结果作为证据，不用主观印象替代事实。

| 维度 | 分值 | 评估重点 |
|------|------|----------|
| 范围与需求匹配 | 15 | 是否完成用户目标和验收标准；是否混入无关变更；是否处理 out of scope。 |
| 实现质量 | 20 | 代码或文档是否简单、可维护、符合既有模式；是否引入不必要抽象或重复。 |
| 测试与验证证据 | 20 | 是否覆盖关键路径、回归路径和等价矩阵；验证命令、退出结果和环境是否明确。 |
| 事实源与流程遵守 | 15 | current-work、Backlog、Requirement、Iteration、Milestone、TD、work-log、spec/plan 是否同步；分支、PR、合并流程是否正确。 |
| 风险与行为变化控制 | 15 | API / DTO / 数据完整性 / 前端生命周期 / 安全 / prompt / 配置变化是否被识别和验证；“行为不变”声明是否有依据。 |
| 可评审性与交接质量 | 10 | PR 范围是否清晰；提交和文档是否能让下一个 AI IDE 或人工快速接手。 |
| 持续改进信号 | 5 | 评审发现是否被修复、入账或转成规则 / 脚本改进；是否避免只停留在聊天记录。 |

## 分数解释

| 总分 | 结论 | 处理方式 |
|------|------|----------|
| 90-100 | 优秀 | 可以关闭；只记录小改进建议。 |
| 80-89 | 良好 | 可以关闭；轻量 follow-up 或下次注意。 |
| 70-79 | 可接受 | 可以有条件关闭；必须登记明确 follow-up。 |
| 60-69 | 有风险 | 不建议关闭；优先修复阻塞项或补验证。 |
| < 60 | 不合格 | 不能关闭；需要回到实现或计划阶段。 |

## Follow-up 分流

评审发现的问题按性质入账，不使用临时 `xxx-FOLLOWUP` 作为长期编号。

| 问题性质 | 任务类型 | 事实源 |
|----------|----------|--------|
| 原需求验收缺口、验收口径不一致、真实业务场景未闭环 | `REQ-xxx` | `docs/01-product-planning/04-backlog.md` 或 `docs/01-product-planning/05-requirements/*` |
| 用户可见错误、回归、异常或线上 / 本地 bug | `BUG-xxx` | `docs/01-product-planning/04-backlog.md`，必要时进入 spec / plan |
| 代码结构、测试基础设施、质量门禁、可维护性问题 | `TD-xxx` | `docs/03-engineering-governance/technical-debt.md` |
| 规则、文档、流程、事实源状态漂移或脚本门禁问题 | `DOC-xxx` | `docs/03-engineering-governance/work-log.md`、对应规则或脚本 |

如果问题属于当前任务完成标准，优先在当前任务内修复；如果不阻塞当前交付但有明确证据，必须进入对应事实源。

## 规则改进判断

不是每个评审问题都需要新增规则。满足以下任一条件时，才建议补规则或脚本门禁：

- 同类问题在不同任务、不同 AI IDE 或不同人员之间重复出现。
- 问题影响事实源可信度、任务关闭判断、发布安全、数据一致性或用户可见行为。
- 问题可以被低成本检查，例如路径、状态、占位文本、候选区数量、旧目录引用或验证声明格式。
- 现有规则已有要求，但入口过深、表述不清或缺少完成前硬检查。

优先级顺序：

1. 能脚本检查的，优先加入 `scripts/engineering/check_engineering_docs.py` 或现有质量门禁脚本。
2. 不能脚本检查但高频高风险的，补到最贴近的规则文件。
3. 一次性误判、低风险表达问题，只写评审建议或复盘记录，不新增长期规则。

## 复盘数据口径

阶段性复盘时可按任务统计以下指标：

| 指标 | 计算方式 | 用途 |
|------|----------|------|
| 平均评分 | 所有已评审任务总分平均值 | 衡量交付质量趋势。 |
| 一次关闭率 | 评分 >= 80 且无必修 follow-up 的任务数 / 已评审任务数 | 衡量任务完成可信度。 |
| 返工率 | 需要 REQ / BUG / TD / DOC follow-up 的任务数 / 已评审任务数 | 衡量计划和验收缺口。 |
| 流程违规率 | 事实源、分支、PR、合并或验证声明扣分的任务数 / 已评审任务数 | 衡量流程遵守稳定性。 |
| 规则转化率 | 形成规则或脚本改进的评审问题数 / 评审问题总数 | 衡量复盘是否转成组织资产。 |

复盘结论应区分“实现能力问题”“规则缺口”“工具习惯问题”和“需求塑形不足”，避免把所有问题都归因到模型能力。
