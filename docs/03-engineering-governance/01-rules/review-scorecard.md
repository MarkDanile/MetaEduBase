# Review Scorecard — 任务评审评分卡

本文件用于统一 Codex、Claude Code、Trae、人工 Review 或 PR Review 的任务评价。评分不是替代门禁，而是沉淀可比较数据。

## 使用时机

- AI IDE 交叉复核任务完成情况。
- 用户明确说“按流程评审”后，对当前待合并 PR 执行正式评审和评分。
- PR 合并前判断是否具备关闭条件；历史复盘评分必须明确标记为 `Backfilled`。
- 阶段复盘需要汇总多个任务质量。
- 同类问题重复出现，需要判断是否补规则或脚本。

跨 3 个以上文件、多 PR / 切片、关闭 `REQ` / `BUG` / `TD` / `DOC`、发现 follow-up 或流程问题时，必须完整评分。

## 按流程评审边界

- “按流程评审”必须针对当前待合并 PR Head 执行完整 100 分评分卡，不因任务较小而省略评分。
- 先检查范围、实现、测试、风险和事实源；当前任务完成标准内的阻塞 finding 优先在同一 PR 修复，非阻塞问题绑定稳定 follow-up。
- 评审修复后重新运行受影响验证，评分结论以最终待合并代码为准；评分记录自身的纯文档提交不使评审失效，评分后其他代码、测试或契约变化必须复核并更新结论。
- 正式评分和 follow-up 写入 `review-score-log.md` 并推送到当前 PR；评分记录本身不代表任务已完成。
- 评审阶段禁止调用 merge 或开启 auto-merge。评分完成后报告结果并停止，等待用户明确下达“按流程合并”等合并指令。

## 首轮复审包

复杂或高风险 PR 在请求独立复审前，PR 描述必须附当前 HEAD SHA 和以下复审包：

- 不变量与状态真值表。
- 来源、类型和 tenant 裁决矩阵。
- 锁序图、事务边界和 lease/CAS 条件。
- 失败、超时、重试、幂等和 late-write 矩阵。
- 测试到不变量的映射、反例和变异判别力。
- 明确不做的范围、剩余风险和事实源同步状态。

首轮复审不得只检查一个触发样例。必须由独立复审方在同一 HEAD 并行覆盖数据/状态、并发/故障、测试/运维/文档三个面，然后由协调者按根因族去重。连续两轮产生新的 P1 时，评审结论必须升级为“先拆分或重构”，不得继续无边界叠加局部补丁。

## 评分落盘

“按流程评审”和其他复杂评审完成后，追加到 `docs/03-engineering-governance/04-retrospectives/review-score-log.md`。只要出现总分、follow-up、流程扣分点、事实源不同步、规则 / 脚本建议，也必须落盘。

落盘字段至少包含：日期、任务、PR、总分、结论、必修 follow-up、流程扣分点、规则 / 脚本改进、评审人。评分类型区分 `Original` 与 `Backfilled`。

## 评分维度

总分 100，必须引用代码、文档、PR、测试命令或验收结果。

| 维度 | 分值 | 重点 |
|------|------|------|
| 范围与需求匹配 | 15 | 目标、AC、out of scope、无关变更 |
| 实现质量 | 20 | 简单、可维护、符合既有模式 |
| 测试与验证证据 | 20 | 关键路径、回归、命令、退出码、环境 |
| 事实源与流程遵守 | 15 | 工作台、Backlog、TD、work-log、分支、PR、合并 |
| 风险与行为变化控制 | 15 | API、DTO、数据、前端生命周期、安全、prompt、配置 |
| 可评审性与交接质量 | 10 | PR 范围、提交、文档、可接手性 |
| 持续改进信号 | 5 | 问题是否修复、入账或转成规则 / 脚本 |

AI Chat、RAG、LLM NER、图谱召回等效果型任务评审时，`测试与验证证据` 必须单独看最高验证层级：代码接入、mock / fixture、dry-run / 真实 PG、真实 LLM / 用户验收。任务声明高于证据层级时，在 `测试与验证证据` 和 `事实源与流程遵守` 中扣分，并登记 follow-up。

## 分数解释

| 总分 | 结论 | 处理 |
|------|------|------|
| 90-100 | 优秀 | 可关闭，记录小建议 |
| 80-89 | 良好 | 可关闭，轻量 follow-up |
| 70-79 | 可接受 | 有条件关闭，必须登记 follow-up |
| 60-69 | 有风险 | 不建议关闭，先补阻塞项 |
| < 60 | 不合格 | 不能关闭，回到实现或计划 |

## Follow-up 分流

| 问题性质 | 类型 | 事实源 |
|----------|------|--------|
| 原需求验收缺口、真实业务场景未闭环 | `REQ-xxx` | Backlog / Requirement |
| 用户可见错误、回归、异常 | `BUG-xxx` | Backlog / Requirement |
| 代码结构、测试基础设施、可维护性 | `TD-xxx` | `technical-debt.md` |
| 规则、文档、流程、事实源漂移、脚本门禁 | `DOC-xxx` | work-log、规则或脚本 |

当前任务完成标准内的问题优先当前修；不阻塞但有证据的问题必须入账。

## 规则改进判断

不是每个问题都要加规则。满足任一条件才补规则或脚本：跨任务 / 跨 AI 重复出现；影响关闭判断、发布安全、数据一致性或用户行为；可低成本脚本检查；现有规则入口过深或缺硬门禁。

优先顺序：能脚本化先脚本化；高频高风险补最近规则文件；一次性低风险只写评审建议。

## 高分质量校准

阶段复盘时，最近 5 条平均分 > 92 必须抽查评分是否偏宽。若发现未登记 follow-up、验证声明缺证据、行为不变无依据、事实源漂移或 PR 范围过大未扣分，在评分总账标记并登记 follow-up。

## 复盘数据口径

常用指标：平均评分、一次关闭率、返工率、流程扣分率、规则转化率。复盘结论区分实现能力、规则缺口、工具习惯和需求塑形不足。
