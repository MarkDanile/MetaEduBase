# Workbench — 当前工作台规范

`current-work.md` 是所有 AI IDE、插件和人工协作的当前任务入口；本文件只记录工作台维护硬规则。

## 使用规则

- 修改 `current-work.md` 或任务状态前，必须先读本文件。
- 任何正在开发、准备开发、阻塞、待验证或刚完成且需交接的任务，都应在工作台有卡片。
- 很小的即时修复或纯问答可不建卡；跨文件开发、计划接力、状态交接必须建卡。
- 任务卡只写当前状态、下一步、验证和交接；长需求、实现步骤、复盘放到 requirement、spec、plan、技术债、PR 或 work-log。
- 会修改仓库文件时，先切任务分支，再更新工作台；不得在 `main` 上写“进行中”。
- 从 Backlog、Requirement、Milestone、Iteration 或技术债点名开工时，先按 `task-modes.md#任务入口解析门禁` 定位事实源；实现前登记到工作台。
- 进入 Git 提交前，最后回读 `current-work.md`，确认状态、验证和下一步与实际一致。
- 完整 Git 闭环后，清除“以最终回复为准”“提交后更新”“待最终确认”等占位。

## 状态流

| 状态 | 含义 |
|------|------|
| `⚪ 待澄清` | 目标或范围不清楚，不能实施 |
| `⚫ 待计划` | 目标清楚，但缺计划 |
| `🔵 就绪` | 计划和验收标准齐全 |
| `🟡 进行中` | 正在开发或走 Git 闭环 |
| `🔴 阻塞` | 缺信息、环境或外部依赖 |
| `🟣 待验证` | 实现完成，等待测试或人工验收 |
| `🟢 完成` | 已验证、PR 已合并、事实源已收口 |

## 状态同步规则

- 开工可写 `🟡 进行中`，并记录分支、执行模式和验证计划。
- 代码完成但验证未完成时写 `🟣 待验证`，不得写“验证通过”。
- PR 未 merge 前不得翻 `🟢 完成`；`gh pr view <PR>` state 必须为 `MERGED`。
- 验证通过但 Git 阶段未完成时，保持活跃状态并写清停在哪一步。
- 提交前不得保留过期 `未运行`、`下一步：提交变更`、`PR / merge commit 以最终回复为准`。

### 正式评分提交例外

正式评分提交只允许按 `review-scorecard.md#正式评分提交不变量` 向评分总账新增一行，不更新 `current-work.md` 的下一步、验证状态或完成状态。评分摘要、任务完成态、候选任务移动以及 `plan` / `work-log` 收口属于 PR 合并后的 docs closeout；Metrics Snapshot 属于独立复盘或治理任务。评分后若需要补充这些事实源，必须离开评分提交原子边界并按对应流程另行提交。

## 保留策略

- `当前进行中`：只保留活跃、阻塞、待验证或正在 Git 闭环的任务；一个 agent 默认只持有 1 个当前任务。
- `当前进行中` 无活跃任务时，只写一句 `当前无活跃任务。`，不要用 `暂无` 表格承载完成摘要或下一步建议。此约束由 `scripts/check-engineering-docs` 的 `current-work-in-progress-pollution` 门禁硬执行：无活跃任务（无表格、无 `### TASK` 卡片）时该区只允许 1 个非空行，>1 行（如追加完成摘要段落）会阻塞 PR。
- `下一批候选任务`：只保留 1 到 3 个近期未完成候选；完整 backlog 回对应总账。
- `最近完成`：最多 20 行；超过时一次性只保留最新 12 行，第 13 行及以后移出。
- 超出窗口的完成任务必须在 `work-log.md` 或对应总账保留索引。

## 区域选择策略

- 从候选区开工：移入“当前进行中”，状态改 `🟡 进行中`，写分支、工具、验证计划。
- 从外部事实源点名开工：先登记到“当前进行中”；Milestone 只能作为规划归属，必须映射稳定任务编号。
- 新发现问题：有证据、完成标准、验证方式才可进入候选区；否则只登记到对应总账。
- 并行模式：工作台只记录批次入口；各 agent 过程状态写各自 plan / PR，由集成者统一回填。

## 并行批次边界

并行批次入口至少写：任务 ID、agent、分支、推荐 worktree / clone、允许范围、禁止范围、冲突点、合并顺序、集成负责人和批次验证计划。并行期间不要高频移动全局工作台状态。
