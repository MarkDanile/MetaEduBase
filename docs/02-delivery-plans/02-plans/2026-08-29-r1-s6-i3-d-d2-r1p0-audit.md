## 1. 核心恢复场景——archive 能否合法表达？

### 1.1 D1a codec 导出字段（实际）

| RECORD_KIND | 表 | 列 |
|---|---|---|
| `operation` | `agent_conversation_purges` | id, tenant_id, conversation_id, state, failure_code, registry_digest, retention_policy_digest, retention_policy_snapshot, hold_revision_snapshot, lease_epoch, purge_revision, scheduled_at, started_at, completed_at, lease_expires_at, next_retry_at, revision, created_at, updated_at |
| `checkpoint` | `agent_conversation_purge_owners` | id, tenant_id, purge_operation_id, owner_key, owner_version, capability_digest, state, attempt, checkpoint_digest, ack_digest, reason_code, created_at, updated_at |
| `external_ref` | `agent_external_object_refs` | id, tenant_id, conversation_id, owner_key, ref_scheme, ref_value, source_table, source_row_id, erase_state, receipt_digest, blocked_reason, created_at, updated_at |
| `reconcile` | `agent_transport_scope_reconcile` | id, tenant_id, owner_key, source_table, source_row_id, conversation_id, reconcile_class, issue_code, state, revision, created_at, resolved_at |

### 1.2 schema 整体可表达性判定

| 维度 | archive 包含 | LIVE DB 包含 | 是否足以完成恢复 |
|---|---|---|---|
| operation state（路由依据） | ✅ | ✅ | **是** — archive 含 `state`，可作路由输入 |
| 六元组（checkpoint 6 字段） | ✅ | ✅ | **是** — archive 含完整 6 字段 |
| operation fence 字段 | ✅ | ✅ | **是** — archive 含 `hold_revision_snapshot / lease_epoch / revision` |
| conversation.title / purge_state | ❌ | ✅ | **否** — archive 不含 conversation；replay 阶段必须用 LIVE conversation |
| fence.state / ingress_digest | ❌ | ✅ | **否** — archive 不含 fence 行；participant 内部自管 |
| registry_snapshot（完整 owners 列表） | ❌（仅 digest） | ✅（实时计算） | **否** — archive 仅含 `registry_digest`；replay 必须用 LIVE registry |

**结论**：archive 足以**驱动路由决策**（operation.state + 六元组），但**不足以重建**完整 conversation / fence / registry snapshot。replay 路径合法：archive 决定 WHAT TO DO，LIVE DB 提供 execution context。这是冻结契约 §S6-8.2 + §S6-13.2 + §S6-13.4 的字面语义。

### 1.3 「archive 含备份时点之后的 purge」场景判定

| 场景 | archive 端 | LIVE DB 端 | 当前 D2 行为 | 判定 |
|---|---|---|---|---|
| archive operation 已存在，DB operation 已删（FK cascade） | 有 | 无 | FACT_DRIFT_OPERATION_MISSING + 零写 | ❌ 错——应区分「合法 cascade 后续删除」与「真实 drift」；**保守零写可接受但 reason_code 需明确** |
| archive operation 已存在，DB operation.state 已 ack | state=acking | state=acked | 路由按 LIVE state=acked → no_repeat | ✅ 正确（archive state 不再可靠；LIVE 是事实源） |
| archive operation 已存在，DB operation.state=acked 但 archive.state=erasing | state=erasing | state=acked | 路由按 LIVE → no_repeat；archive state 被覆盖 | ⚠️ 需明确路由规则——TOCTOU 风险 |
| archive operation 已存在，DB operation.state=running 但 archive.state=acked | state=acked | state=running | 路由按 LIVE=running → candidate_when_local | ⚠️ archive 显式记录已 ack；按 LIVE 重跑可能违反 idempotency |
| archive checkpoint.state=acking 但 DB=acked | state=erasing | state=acked | 路由按 LIVE=acked → no_repeat | ⚠️ 同上 |
| archive owner=workspace.core 但 DB owner=execution.core（owner 重排） | workspace.core | execution.core | 路由按 LIVE owner_key → 走错 owner | ❌ **drift**——reason code 缺 |

**核心问题**：

P0-1：当前代码路由用 **LIVE DB state**（在 pass B 内读 operation.state），但冻结契约 §S6-12.1 字面是路由按 **archive-recorded state**（archive 是冻结事件账本）。TOCTOU：pass A 验证后到 pass B 执行之间，DB state 可能被 retention worker 推进。

P0-2：`reason_code` 字段缺失——drift 失败时无法定位是 6 元组哪一项不一致（state / owner_version / capability_digest / ack_digest / owner_key / purge_revision）。

P0-3：transport owner 入口错——当前用 `erase_transport_body`（subclass-only body helper，**没有 fence / owner lock / expected revision**），应改用 `erase_transport_owner`（parent class 主入口，含 Conversation→owner→fence→aggregate 全锁序 + expected_operation_revision CAS）。

P0-4：Phase 1 用 caller 的 `PublishOutcome` 当 archive 证明——这违反「commit-graph 必须从 D1b committed tip 验证」契约（caller 可伪造 marker）。应改用 `asyncio.to_thread(find_committed_tip)` + `fetch_segment_bytes`，无 tip / fork / corrupt 即 fail closed。

P0-5：Gate API 接受 `replay_blocking_count: int = 0` 默认参数——caller 可传 0 绕过阻断。须强制接收 `RestoreReplayReport` 并从 report 内部 derive（`error` / `owners_fact_drift` / `owners_non_local_blocked` / `runtime_binding_evidence_unprovable` / `external_verify_only` 全部阻断）。

P0-6：Gate `s6_6_findings` 字段声明存在但实际实现里恒为空 tuple（`s6_6_findings: tuple[tuple[str, int], ...] = ()`）——声称已 reuse `verify_inspection` 但 report.inspections 被丢弃。

P1-7：测试含「`_execute_local_owner_via_participant` 函数体无 `try:`」（grep 字符串检查）——这是反模式（mutation KILL 不可观测）。须替换为真实双 owner 失败测试（owner A 成功 + owner B 抛错 → A/B/正文/fence/checkpoint 全部保持原值）。

P1-8：mutation kill 只 3 条（M-D2-1/3/6），缺 P0 暴露的关键路径——committed-tip bypass、transport 主入口降级为 body helper、单 drift 仍执行其他 owner、purge_revision / ack_digest 对账删除、gate 忽略 replay report。
