# 前端 UI 基础设计升级方案：右侧主内容区审美与主题系统重构

> 日期: 2026-05-22
> 状态: 设计已确认，待进入实施计划
> 范围: 前端右侧主内容区基础设计系统 + 多主题抽象层 + 后续逐页适配策略

---

## 1. 目标概述

本次升级的目标不是给现有页面“换皮”，而是把前端右侧主内容区升级为一套稳定、克制、可复用的内容工作台设计系统。

重点目标：

- 在所有主题下，右侧主内容区都保持极简、干净、长期使用不疲劳
- 减少背景装饰、材质噪声和过强的视觉表演，避免喧宾夺主
- 将主题差异收敛为轻量、可控的 token 差异，而不是散落在组件和页面中的大段覆写
- 先建立统一的基础设计系统，再逐页审查并重构各业务页面

本次审美方向以 Linear / Vercel 风格的冷静秩序感为主：强调留白、节奏、层次和信息优先级，而不是强调材质效果本身。

---

## 2. 当前问题总结

当前前端已经具备四套主题和一批通用样式 token，但右侧主内容区仍存在以下问题：

1. **内容区气质不统一**
   - 主题存在，但“页面工作区”的信息密度、背景克制程度、卡片层级感没有被统一设计
   - 页面更像是使用了一组主题色，而不是共享同一套稳定的内容设计系统

2. **主内容区背景表达偏重**
   - 右侧内容区当前通过背景纹理、径向 glow、scan 动效、hover 抬升等方式建立氛围
   - 在长期使用场景下，容易让背景与容器本身抢走注意力

3. **抽象层级不够稳定**
   - 当前通用类名以 `liquid-*` 为主，语义偏绑定某一种风格
   - 多主题下继续沿用 `liquid-card`、`content-bg`、`liquid-btn` 的命名，不利于长期演进为真正的多主题设计系统

4. **主题覆写方式维护成本较高**
   - 当前主题不仅定义颜色 token，也直接覆写组件类行为
   - 这会导致新增主题或调整设计规则时，需要同时修改 token、基础组件类和主题专属覆写块

5. **页面收敛能力不足**
   - 若不先建立统一右侧工作区骨架，后续逐页重构时容易再次出现页面私有容器、私有层级和私有交互密度

---

## 3. 设计原则

### 3.1 信息优先
主内容区首先是信息工作区，不是视觉展示区。背景、材质和装饰都必须退后，容器仅承担组织信息的作用。

### 3.2 弱差异统一
四套主题共享同一套布局、留白、容器层级和交互密度，仅保留轻量的色彩气质与边框/焦点风格差异。

### 3.3 语义化抽象
页面和组件不再依赖“某种视觉风格类名”，而依赖“语义化容器和交互层”。视觉变化尽量通过 token 驱动。

### 3.4 克制层级
优先通过留白、边框、轻底色和局部对比建立层级，不依赖重阴影、强渐变和频繁动画。

### 3.5 先系统，后页面
先建立统一的右侧工作区基础设计系统，再逐页适配业务页面。页面重构必须服从基础系统，而不是反过来由页面定义系统。

---

## 4. 目标用户体验

升级完成后，用户在任一主题下进入右侧主内容区时，应感受到：

- 背景安静，内容边界清晰
- 页面之间像同一产品中的不同功能，而不是不同模板
- 卡片和面板存在感适中，不会抢走信息主层级
- 主按钮、选中态、焦点态清晰但不刺眼
- 连续工作时视觉负担低，适合管理、检索、浏览、编辑等中高频操作场景

---

## 5. 总体方案

采用“统一内容壳 + 语义化 surface tokens + 轻主题差异”的基础设计方案。

这套方案分成两层：

1. **基础设计系统层**
   - 定义右侧主内容区画布、页面骨架、区块容器、工具栏容器、信息面板容器
   - 将当前基于风格命名的容器类收敛为语义化容器类
   - 将主题差异尽量收缩到 token 层

2. **页面适配层**
   - 基于新的语义容器，对首页及各业务页面进行逐页审查与重构
   - 每个页面优先复用统一骨架和容器，不新增页面私有视觉协议

---

## 6. 右侧主内容区基础骨架

右侧主内容区将被重构为统一的“内容工作台骨架”。

### 6.1 骨架层级

建议形成以下语义层：

- `app-canvas`：右侧整块工作区画布
- `ui-page-shell`：单页外层容器，控制最大宽度、横向 gutter、顶部节奏
- `ui-page-header-block`：页面标题区，统一标题、副标题、操作按钮的垂直节奏
- `ui-page-section`：页面区块，用于组织统计区、筛选区、列表区、详情区等
- `ui-panel`：标准内容容器
- `ui-panel-muted`：更轻的容器，用于辅助信息、筛选区域、次级块
- `ui-panel-ghost`：几乎无背景、主要依靠间距和分割线组织内容的轻容器
- `ui-toolbar`：搜索、筛选、批量操作等工具条容器

### 6.2 骨架规则

- 页面宽度统一，避免某些页面过窄、某些页面过宽
- 页面顶部到首区块的节奏统一
- 区块之间间距统一，不允许页面私有大幅偏离
- 标准信息容器统一边框、圆角、阴影和 hover 规则
- 页面内组件优先落在语义容器里，而不是裸露堆叠

---

## 7. Token 抽象分层

当前主题 token 具备基础颜色层，但缺少“主内容区语义 token”。本次升级需要补齐抽象层。

### 7.1 分层模型

#### 第一层：Theme Tokens
表示主题原始风格取值，例如：

- `--theme-bg-base`
- `--theme-bg-elevated`
- `--theme-border`
- `--theme-accent`
- `--theme-accent-bg`

#### 第二层：Semantic UI Tokens
表示页面系统真正消费的语义变量，例如：

- `--canvas-bg`
- `--canvas-top-glow`
- `--canvas-grid-opacity`
- `--panel-bg`
- `--panel-bg-muted`
- `--panel-border`
- `--panel-border-strong`
- `--panel-shadow`
- `--panel-shadow-hover`
- `--interactive-hover-bg`
- `--interactive-active-bg`
- `--focus-ring`
- `--content-max-width`
- `--content-gutter`
- `--section-gap`
- `--panel-radius`

### 7.2 设计约束

- 新主题优先通过 Theme Tokens 提供差异值
- 组件类和页面类优先消费 Semantic UI Tokens
- 减少基于主题名直接覆写 `.content-bg`、`.liquid-card`、`.nav-item` 等组件行为的做法
- 若某主题确有特殊表现，优先新增 token，而不是复制一套专属组件规则

---

## 8. 视觉规则

### 8.1 背景

右侧主内容区背景默认应接近纯净底色。

规则：

- 默认不使用明显网格、噪点、强径向 glow 或大面积装饰背景
- 若保留氛围感，只允许极弱程度的顶部层次变化
- 背景存在的意义仅是区分应用画布与内容容器，而不是形成视觉主题主角

### 8.2 容器

规则：

- 面板优先靠边框、极浅底色和留白建立层级
- 默认取消或显著减弱浮起感 hover
- 阴影仅作为极弱补充，不作为主层级手段
- 面板必须稳定克制，避免每个模块都显得“可点击”或“漂浮”

### 8.3 强调色

规则：

- 强调色主要用于主按钮、选中态、焦点态、关键标签和局部数值
- 不用强调色铺大面积块面
- 同屏强调点数量受控，避免在统计卡、操作按钮、图标底、列表状态上同时高频使用

### 8.4 动效

规则：

- 页面入场动效简化，避免明显 blur、scale、扫光效果
- hover 采用轻微边框/底色变化，不采用明显抬升或材质扫光
- 动效只服务于状态反馈，不服务于主题氛围营造

---

## 9. 主题策略

本次采用“弱差异统一”策略。

### 9.1 统一部分

所有主题共享：

- 页面骨架
- 容器语义
- 内容密度
- 标题层级
- hover/focus 交互模型
- 大部分组件形态

### 9.2 差异部分

各主题允许差异存在于：

- 基础背景温度
- 强调色气质
- 边框对比度
- 聚焦态 ring 风格
- 极轻量的面板材质差异

### 9.3 预期效果

- `liquid`：不再强调玻璃存在感，收敛为更清透、轻微柔和的现代主题
- `ink`：保持温润纸感，但右侧内容区避免过强“文人感”材质表达
- `navy`：保留稳重感，但不依靠厚重深色质感堆出“奢华感” 
- `notion`：继续保持冷白极简，但纳入统一骨架与交互标准

---

## 10. 命名与组件策略

当前大量通用类以 `liquid-*` 命名，不适合作为长期多主题设计系统的核心语义。

### 10.1 命名调整方向

新增或逐步替换为：

- `ui-page-shell`
- `ui-page-section`
- `ui-page-header-block`
- `ui-panel`
- `ui-panel-muted`
- `ui-panel-ghost`
- `ui-toolbar`
- `ui-empty-surface`
- `ui-interactive-row`

### 10.2 兼容策略

- 短期允许现有 `liquid-*` 类与新 `ui-*` 类并存
- 中期以 `ui-*` 语义类为主，逐步减少 `liquid-*` 在页面层的直接使用
- 若某些旧类保留，仅作为底层实现别名，而不再作为页面设计语言核心

### 10.3 组件化边界

本阶段优先抽样式协议，不急于为所有容器新建 Vue 组件。

原则：

- 高频重复结构可后续抽为组件
- 低频结构先复用 class 和 token 即可
- 避免为了抽象而抽象，保持实现成本可控

---

## 11. 实施阶段

### 阶段 1：基础设计系统建设

目标：先稳定右侧主内容区的统一基础规则。

范围：

- 重构主内容区画布样式
- 定义内容区语义 token
- 增加统一 page shell / page section / panel / toolbar 类
- 收缩主题覆写到 token 层
- 简化过重背景、hover、动效和面板材质
- 选择一个基准页面验证新系统

基准页面建议：`HomeView.vue`

原因：

- 覆盖统计卡、功能入口卡、快捷操作、动态列表等多种常见结构
- 容易暴露容器层级、强调色密度、标题节奏和 hover 规则问题
- 一旦首页成立，后续页面能复用较多模式

### 阶段 2：逐页审查与重构适配

在基础系统稳定后，再逐页适配以下页面：

1. 知识库
2. 资源库
3. 数据库
4. AI 问答
5. 管理页 / 技能编排等辅助页面

逐页审查时，每页都要检查：

- 是否使用统一 page shell
- 是否使用统一 section gap
- 是否存在过重卡片样式
- 是否滥用强调色
- 是否存在私有 panel 样式应回收
- 是否存在背景或动效抢夺注意力
- 是否能在四主题下保持一致可读性

---

## 12. 验收标准

### 12.1 视觉验收

- 任一主题下，右侧主内容区的第一感知是内容，而不是背景或材质
- 页面背景明显比当前更安静
- 卡片和容器的存在感下降，但信息层级更清晰
- 页面间视觉骨架一致
- 长时间浏览不会出现明显花哨或视觉疲劳

### 12.2 系统验收

- 页面能够通过统一语义类完成主要布局和容器组织
- 新主题接入不需要复制一套页面组件样式
- 主题差异主要由 token 提供，而不是 scattered overrides 提供
- 基准页与后续业务页使用一致的主内容区协议

### 12.3 实施边界

本次不包括：

- 左侧导航信息架构重构
- 业务逻辑改写
- 与 UI 审美无关的功能重做
- 过度组件化或提前抽象大量新 Vue 组件

---

## 13. 风险与约束

1. **抽象过度风险**
   - 若一开始同时重命名全部旧类并拆组件，实施成本会明显上升
   - 因此应先建立 token 和语义类，再逐步迁移页面使用方式

2. **主题个性损失风险**
   - 弱差异统一可能让各主题看起来更接近
   - 这是有意取舍，目标是优先保证长期使用体验和维护效率

3. **页面遗留样式回流风险**
   - 若页面保留太多私有类，后续仍会重新分叉
   - 因此逐页重构时必须同步回收共性到基础系统

4. **首页基准失真风险**
   - 若仅在首页中验证成功，但无法覆盖列表、表单、详情等常见模式，则抽象会不完整
   - 因此首页验证后必须尽快进入业务页复核

---

## 14. 建议实施顺序

1. 重构主内容区 token 分层
2. 重写右侧画布与基础容器类
3. 用首页建立基准页
4. 审查并适配知识库页面
5. 审查并适配资源库页面
6. 审查并适配数据库页面
7. 审查并适配 AI 问答页面
8. 审查并适配剩余辅助页面
9. 最后统一按钮、列表、空状态、详情容器密度

---

## 15. 结论

本次 UI 升级采用“统一内容壳 + 语义化 surface tokens + 轻主题差异”的策略。

先把右侧主内容区升级为一套稳定、克制、语义清晰的基础设计系统，再逐页重构业务页面，使所有主题下的工作区都保持极简、干净、长期使用不累，并且在实现层面具备高抽象度和可维护性。
